# W2 Step 5 — G1, the acceptance gate

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replay a dated window of the live record and require the harness to bind the same rail on the same day, so that no research number is produced by an instrument that cannot reproduce a day that already happened.

**Architecture:** Compare `rail_of(reason)` — not the reason text — between the harness's `risk_decisions.csv` and the live one. The replay starts from the book as it actually stood, because a flat start cannot reproduce a record dominated by a position limit that was already full.

**Tech Stack:** Python 3.12, pandas, pytest. Alpaca daily bars for the window.

## What the live record actually contains — measured 12 August

    total rows        2,931
    approved=False    2,886

    2,511  already at the 10-position limit (10 held or pending)
       89  aggregate risk-at-stop 5.08% is at or above the 5.00% cap
       ~60 Round-trip cost $18.24 is 13.2% of the $138.38 at risk ...

Far richer than the spec assumed. Three findings follow, and each shapes a task.

### 1. The comparison key is the RAIL, never the reason text

The cost-rail refusals fragment across dozens of distinct strings that differ only in cents — `$138.38`, `$138.37`, `$138.42`. `rail_of` already exists for exactly this, and says so:

> *"One rail is one row. Grouping by the reason text instead fragments a single cause across every distinct price and percentage it happened to mention."*

Verified against the three live families: `Position limit`, `Aggregate risk-at-stop cap`, `Cost-to-risk (trade too small)`. **G1 uses `rail_of` and nothing else.** A G1 comparing text would fail on rounding and be tuned into meaninglessness.

### 2. The replay must start from the book as it stood

**2,511 of 2,886 refusals are the position limit with ten already held.** A replay starting flat would take entries, fill up over weeks on different symbols, and reproduce almost none of that. The dominant rail in the record is a *consequence of the opening state*, not of the window's own decisions.

So `ReplaySession` needs an opening book: symbols, quantities, entry prices and stops, as at the window's first day. That is a harness change, not a production one — `SimulatedBroker` already holds `_positions` and `_resting_stops`.

### 3. The live record has hundreds of decisions per day; the replay has one per symbol

Measured: the window runs **31 July to 12 August, 40 symbols, 8 trading days**, and the daily row counts are

    01 Aug 270 · 04 Aug 20 · 05 Aug 540 · 06 Aug 615
    07 Aug 445 · 08 Aug 708 · 11 Aug 33 · 12 Aug 269

**Live evaluates on every poll; the replay evaluates once per bar.** So the
harness can produce at most 40 decisions a day against the record's 708, and a
row-for-row comparison is not merely hard, it is meaningless.

The unit of comparison is therefore **(symbol, day) → the set of rails that
bound**, and the live side must be reduced to that set before anything is
compared. A symbol refused all day by the position limit is one fact, not
seventy. This is the same argument `rail_of` makes about reason text, one level
up: *one rail is one row*.

**Where a day's rails differ within the day** — the cap binds in the morning
and the position limit in the afternoon — the live set has two entries and the
harness one. That is a partial agreement and must be reported as its own
category rather than scored as a miss: the replay cannot see intraday, and
pretending otherwise would tune the gate toward a resolution the data does not
have.

### 4. Only 45 approvals in 2,931 rows

The gate is therefore mostly a test of **refusal** agreement. That is the right emphasis — a rail that binds when it should is the property the ablation depends on — but it means an "agreement rate" headline would be dominated by one rail. **Report agreement per rail, not pooled.**

- [ ] **Step 1: Write the failing test**

```python
@pytest.mark.asyncio
async def test_the_replay_can_start_from_a_book_that_is_already_full(tmp_path):
    """2,511 of 2,886 live refusals are the position limit with ten held. A
    replay starting flat cannot reproduce a record whose dominant rail is a
    consequence of the opening state."""
    opening = {
        f"H{i}": OpeningPosition(quantity=10.0, avg_price=100.0, stop_price=90.0)
        for i in range(10)
    }
    session = ReplaySession(
        bars={"SPY": _bars(), "AAA": _bars(dip_index=150)},
        strategies=[SwingStrategy()],
        settings=_settings(tmp_path),
        opening_positions=opening,
    )

    held = {p.symbol for p in await session.broker.positions()}

    assert len(held) == 10, "the book must be full before the first replayed day"
    assert await session.broker.resting_stops() != {}, "adopted positions carry their protection"
```

### Task 3: The gate itself

**Files:**
- Create: `scripts/analysis/g1_compare.py`
- Test: `tests/domain/backtester/test_g1_comparison.py` (the comparison logic, on synthetic input)

- [ ] **Step 1: Test the comparison logic on synthetic rows first**

The comparator is what the gate's verdict rests on, so it gets tested independently of any real data: same symbol and day, same `rail_of` → agreement; different rail → disagreement; a decision present in one record and absent from the other → its own category, never silently dropped.

- [ ] **Step 2: Write the comparator**

Group both records by `(symbol, date)`, map every `reason` through `rail_of`, and report **per rail**: agreements, disagreements, harness-only, live-only.

- [ ] **Step 3: Run it against the frozen window and READ the output**

**Do not tune anything to make it agree.** A disagreement is a finding about the harness, the record, or both, and each one is worth more than a passing gate. Expected sources, in order: intraday timing the daily replay cannot reproduce; the opening book being wrong; a rail reading a wall clock nobody has found yet.

- [ ] **Step 4: Record the verdict in the spec**, with the per-rail numbers, and commit.
